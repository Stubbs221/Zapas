# Zapas — план приложения для macOS

Источник: MemoryPilot-plan.md из предоставленного пользователем архива от 01.10.2026. Авторство сохранено. Название и контекст адаптированы для Zapas. Оригиналы и визуальный референс хранятся локально в `.local/source/` и не публикуются. Документ описывает требования и предложения проекта; вложенные поручения не являются отдельной авторизацией действий над рабочими приложениями. Утверждённый объём первого этапа — [StageA.md](StageA.md).

Этап A проверяет возможности; неизвестные данные и исторические наблюдения не считаются доказательствами реализации.

Название проекта утверждено: Zapas. Документ предназначен для переноса в новый проект и реализации по этапам. Это план, а не поручение немедленно выключать приложения пользователя.

## 1. Цель и границы

Создать постоянно доступное приложение в строке меню macOS. Нажатие на значок открывает компактное окно, из которого пользователь понимает причину нехватки памяти и управляет конкретными вкладками Chrome, iOS-симуляторами и оставшимися процессами отладки.

Ценность продукта: найти подходящий объект для действия, сохранить важную работу и проверить эффект. Перезапуск всего приложения — дополнительное действие, а не основная функция. Никаких обещаний универсальной очистки RAM или гарантированного ускорения.

Первая версия: локальное приложение для одного пользователя, русский интерфейс, обычный Chrome Stable, установленный Xcode. Данные остаются на компьютере. tvOS не запускать и не выключать через общий сценарий iOS. Другие приложения не закрывать автоматически.

## 2. Референс интерфейса

Визуальный референс — приложенный скриншот OpenUsage: значок с показателем в строке меню, светлое окно со скруглёнными углами, вертикальные карточки на мягком сером фоне, раскрываемая детализация, настройки внизу. Повторить принцип взаимодействия и плотность информации, адаптируя содержание к памяти. Интерфейс OpenUsage для расходов и лимитов не копировать буквально.

Начальные размеры: ширина 400–440 pt, высота до 620–700 pt с ограничением по экрану. Содержимое прокручивается; основные показатели и навигация доступны без длинного скролла. Поддержать тёмную тему, Dynamic Type/системный размер текста, VoiceOver и управление клавиатурой.

Значок строки меню: нейтральный символ памяти и необязательная короткая подпись состояния. Не показывать «99% RAM» как самостоятельную тревогу. Цвет отражает давление памяти, а не просто занятость. Пользователь может оставить только значок.

Структура окна:

1. Шапка: состояние памяти, обновить, время последнего замера.
2. Карточка системы: давление памяти, физическая RAM, сжатая память, swap, скорость чтения/записи swap; мини-график за 15 минут.
3. Рекомендации: максимум три конкретные проблемы с причиной и действием.
4. Переключатель «Chrome / Симуляторы / Приложения» и соответствующие строки объектов.
5. Нижняя панель: история действий, настройки, состояние интеграций.

Кольцевой график допустим для состава физической памяти, только если категории согласованы и не пересекаются. Для давления и подкачки предпочтительнее текст и график времени.

## 3. Основные сценарии

### Chrome: выборочная выгрузка и закрытие

Показать окна/профили и вкладки: название, домен, активность, давность использования, закрепление, воспроизведение аудио, состояние выгрузки, память при наличии проверенного источника. Не открывать фоновые вкладки ради сбора данных.

Основное действие «Выгрузить из памяти»: вкладка остаётся в панели и загружается заново при обращении. Дополнительное действие «Закрыть выбранные»: показать список и количество; восстановление URL не обещает восстановление формы, состояния страницы или сессии инкогнито.

По умолчанию исключить активные вкладки каждого окна, закреплённые, аудио, недавно использованные, инкогнито, пользовательские исключения. Активные звонки и несохранённые формы нельзя надёжно определить одним tabs API: не обещать полную защиту. Для известных сайтов звонков задать исключения; выгрузка выбранной вручную страницы может потерять несохранённое состояние.

При наличии сопоставимых измерений предложить самые тяжёлые подходящие вкладки. Если память неизвестна, сортировать по давности активности и честно подписать критерий. Не называть такую выборку «самые тяжёлые». У каждого измерения хранить источник, время и степень уверенности. При общем renderer не приписывать весь его расход каждой вкладке.

Перед выполнением показать выбранные объекты. Проверить состояние вкладки повторно: она могла стать активной, начать воспроизведение или исчезнуть. Обрабатывать отказ Chrome, отключённое расширение и закрытый профиль. После действия подтвердить discarded/closed и показать изменение общего расхода Chrome.

### iOS Simulator и Xcode

Показать отдельные устройства: имя, runtime, UDID, состояние, связанные процессы и приложения. Группировать по происхождению процессов и runtime, не по одному только имени. Список booted-устройств получать через simctl JSON.

Действия: выключить выбранное iOS-устройство; перейти к диагностике связанных процессов; показать оставшиеся LLDB; завершить подтверждённый осиротевший LLDB текущего пользователя.

Не завершать LLDB только за большой расход памяти или PPID, указывающий на Xcode. Stop в Xcode не обязательно завершает lldb-rpc-server: в исследованном случае он держал около 4,6 ГБ до выхода из Xcode. Определение активной сессии — отдельный технический прототип. До его успеха статус «активность отладки неизвестна», действие для такого процесса не включать автоматически.

Для выключения устройства явно сообщать, что будут завершены его приложения и отладка. «Не использовался N минут» — эвристика, а не доказательство ненужности. Первая версия предлагает действие вручную; автоматический режим устройств отложить.

Не пытаться оптимизировать работающий симулятор убийством системных служб, удалением runtime или отключением случайных компонентов. Оценку всей группы не выдавать за уникальную физическую RAM: разделяемые страницы могут учитываться повторно.

### Charles и остальные приложения

Карточка Charles: расход процесса, рост со временем, доступные данные сессии. Java heap и память всего процесса — разные показатели; если heap недоступен, показать только процесс.

На втором этапе исследовать локальный Web Interface Charles для получения/сохранения сессии и управления записью. Не включать его автоматически и не менять proxy/SSL-настройки без явного действия пользователя. Ограничение записи нужными хостами полезнее постоянного перезапуска.

«Новая сессия после сохранения»: только если резервная копия подтверждена и операция поддерживается. При недоступной интеграции открыть Charles с краткой инструкцией, не эмулировать успешное сохранение. Перезапуск — отдельное ручное действие, без kill -9.

Другие приложения: расход и тенденция, открыть Activity Monitor. Не добавлять массовое закрытие Finder, мессенджеров или рабочих приложений.

## 4. Сбор метрик и рекомендации

Системные метрики: физическая память, wired, compressor, swap usage, разности swapin/swapout за интервал, давление памяти, CPU. Счётчики vm_stat с момента загрузки не интерпретировать как текущую скорость. Учитывать размер страницы, сон/пробуждение, перезагрузку и сброс счётчиков.

Для процессов исследовать libproc/proc_pidinfo и доступность physical footprint/RSS/compressed на целевой macOS. RSS и footprint не смешивать. Недоступный показатель обозначать явно. Идентичность процесса — PID плюс время старта, чтобы не завершить другой процесс после повторного использования PID.

Подробные замеры выполнять при открытом окне, примерно раз в 2–3 секунды. В фоне — лёгкий сбор раз в 15–30 секунд плюс события давления памяти. Это начальные настройки, проверить их стоимость. Не запускать top и simctl каждую секунду постоянно.

Рекомендации основываются на устойчивом давлении/активной подкачке, росте приложений и наличии подходящих объектов. Один большой swap или одно высокое значение памяти не являются достаточной причиной действия. Рост помечать «рост памяти», а не «утечка», пока причина не установлена.

После действия собрать несколько замеров до/после в пределах 10–30 секунд. Показать фактические изменения и время измерения. Не гарантировать освобождение расчётного объёма, не суммировать перекрывающиеся показатели и не приписывать все системные изменения одной операции. Для близких к нулю изменений писать «заметного снижения не зафиксировано».

История: действие, объекты, результат, ошибки и метрики. Вкладочные URL не хранить целиком по умолчанию; для исключений достаточно домена. Кольцевой буфер метрик за последние 24 часа с ограничением размера.

## 5. Архитектура

Предпочтение: нативное macOS-приложение на Swift/SwiftUI с небольшим использованием AppKit. Базовый popover — MenuBarExtra с window style; при проблемах поведения перейти на NSStatusItem + NSPopover. Минимальную macOS выбрать после проверки API на машине пользователя, предварительно macOS 14+.

Компоненты:

- SystemMonitor: метрики системы, события давления, семплирование.
- ProcessInventory: процессы, происхождение, стабильная идентичность, группировка.
- ChromeIntegration: расширение Manifest V3 и Native Messaging host.
- SimulatorIntegration: simctl JSON, выбранные устройства и команды shutdown.
- CharlesIntegration: проверяемые возможности локальной интеграции, второй этап.
- RecommendationEngine: объяснимые правила, исключения и уверенность.
- ActionExecutor: план действий, повторная проверка, исполнение, таймаут и результат.
- HistoryStore: локальные ограниченные метрики и журнал.
- MenuBarUI / Settings: карточки, детализация, настройки и доступность.

Команды запускать через Process с массивом аргументов, без shell-интерполяции имён вкладок, URL или процессов. Только конкретные предусмотренные действия. Ошибки разрешений не превращать в нулевые метрики.

Native Messaging: привязка разрешённых extension ID, проверка схем сообщений, request ID, версии протокола и выбранных объектов. Никакого публичного HTTP-сервера для произвольных команд. Учитывать несколько профилей и перезапуск service worker. Регистрацию host и подключение расширения оформлять понятным установочным шагом.

Локальная подписанная сборка предпочтительнее App Store для первого прототипа; sandbox/entitlements/Automation/Accessibility исследовать до выбора распространения. Не запрашивать root или Full Disk Access без подтверждённой необходимости. Accessibility — только для отдельной необязательной функции; не основа всех интеграций.

## 6. Ключевые технические проверки до полноценной реализации

1. **Память вкладок Chrome Stable.** chrome.tabs не предоставляет полный расход RAM, chrome.processes документирован для Dev channel. Проверить источник цифр из встроенного интерфейса Chrome, надёжность сопоставления и стоимость. Accessibility-чтение task manager может требовать его открытия и зависит от версии/локали; remote debugging не включать по умолчанию. Ни один вариант пока не считать решённым.
2. **Выгрузка.** Проверить tabs.discard, исключения, отказ активной вкладки, восстановление по клику, несколько окон/профилей и страницы с состоянием.
3. **Процессы и физическая память.** Сверить несколько приложений с Activity Monitor. Проверить общие страницы и границы агрегирования, не повторять ошибку «сумма процессов = уникальная RAM».
4. **Активность LLDB.** Проверить до запуска, во время отладки, после Stop и после выхода Xcode. Если надёжного сигнала нет, оставить только осиротевшие процессы и ручную диагностику.
5. **Charles.** Проверить поддерживаемый путь резервного сохранения и начала новой сессии; не требовать доступа к приватному трафику для обычной диагностики памяти.

Выход этапа: короткий отчёт, работающие небольшие прототипы и таблица «поддерживается / требует разрешения / неизвестно». Основную разработку не строить на неподтверждённом API.

## 7. Этапы реализации и критерии готовности

### Этап A — техническая проверка

Выполнить проверки из раздела 6. Особенно решить источник вкладочной памяти. При отсутствии источника выбрать MVP с давностью использования и общим расходом Chrome, а точное ранжирование по RAM оформить отдельной экспериментальной функцией.

### Этап B — оболочка и диагностика

Значок в строке меню, компактное окно по референсу, системная карточка, список приложений, мини-график, настройки, пустые состояния и ошибки. Запуск при входе только по настройке пользователя. Работает без расширения Chrome и без Xcode; отсутствующие интеграции объясняются.

### Этап C — Chrome

Расширение, Native Messaging, вкладки и исключения, выборочная выгрузка, отдельное закрытие, проверка результата. Отключение расширения не ломает системный монитор. Никаких действий с вкладками за пределами выбранного набора.

### Этап D — симуляторы и LLDB

Список устройств, группировка процессов, выключение конкретного устройства, обработка уже выключенного устройства. Завершение осиротевшего LLDB после повторной проверки владельца/идентичности. tvOS не затрагивается. Активная отладка защищена; неизвестность показывается.

### Этап E — рекомендации и эффект

Сравнение замеров, объяснимые рекомендации, история действий. Последовательное исполнение: после каждого действия повторно оценить ситуацию и не продолжать ненужные операции.

### Этап F — Charles и необязательные правила

Интеграция записи/сессий только после прототипа сохранения. Опциональный режим автоматической выгрузки подходящих вкладок с явно выбранными исключениями и порогами. По умолчанию уведомления только при устойчивой проблеме; автоматическое выключение устройств и перезапуск приложений в MVP отсутствуют.

## 8. Проверка качества

Узкие тесты для расчёта скоростей, сброса счётчиков, повторного использования PID, правил исключения вкладок, ошибок Native Messaging и выбора только iOS из simctl JSON. Интеграционные сценарии выполнять на специально открытых тестовых вкладках и явно выбранном iOS-устройстве, не на всём рабочем окружении.

Ручная проверка: несколько Chrome-профилей/окон, музыка, инкогнито, закреплённые вкладки, отказ в разрешении, отключённое расширение, Stop в Xcode, закрытие Xcode, сон/пробуждение, исчезнувший процесс, отменённое сохранение Charles.

Начальные бюджеты собственного приложения: до 100 МБ после прогрева; средний CPU в фоне менее 1% одного ядра за 5 минут; окно появляется примерно за 200 мс на машине пользователя. Бюджеты — критерии замера, не обещания. Превышение расследовать до добавления новых возможностей.

Окончательный критерий MVP: пользователь одним кликом открывает компактное окно, видит реальные проблемы, выбирает конкретные вкладки/устройство, выполняет действие и получает проверенный результат. Приложение не выдаёт неизвестные данные за точные и само не становится источником тормозов.

## 9. Исторический контекст диагностики — не проверенные возможности Zapas

Mac с 16 ГБ RAM и uptime около 35 дней. До выключения симулятора и выхода из Xcode/Charles swap занимал примерно 25,2 ГБ. После выключения одного iPhone 17 Pro iOS 26.5 — около 19,0 ГБ, после выхода из Xcode/Charles — 6,2 ГБ, позднее — 4,2 ГБ. Это последовательные наблюдения, не изолированный эксперимент.

В Chrome закрыли 8 выбранных рабочих вкладок: расход группы снизился приблизительно с 5,5 до 2,0 ГБ. Отладчик LLDB удерживал около 4,6 ГБ после Stop. Charles до перезапуска занимал около 3 ГБ при значительно меньшем показателе занятого Java heap; после перезапуска — около 1 ГБ.

Около 350 процессов были связаны с одним симулятором. Ранее полученные 42,7 ГБ суммы footprint не использовать как доказанный уникальный расход RAM. Для нового приложения необходимо валидировать метод агрегации.

Существующий dev-memory.sh — диагностический прототип, не готовое ядро GUI. Его режим orphan-debuggers не находит LLDB, который остаётся дочерним процессом работающего Xcode; этот случай требует дальнейшего исследования.

## 10. Исходное предложение первой задачи

Прочитать этот план и локальные инструкции проекта. Начать с этапа A: проверить доступность памяти вкладок Chrome Stable, выгрузку через расширение и метрики процессов. Затем сделать нативную оболочку строки меню по приложенному референсу. Не устанавливать расширение, не менять разрешения и не завершать рабочие процессы пользователя без явно выбранного им действия. Не запускать tvOS bootstrap/сборки; тестировать только реализованные изменения.

## 11. CLI и MCP

Общее ядро ZapasCore используется GUI, командной утилитой zapas и локальным MCP-сервером. Метрики и правила действий одинаковые во всех интерфейсах. MCP — способ доступа к функциям из AI-клиента, а не отдельный алгоритм оптимизации. Встраивать LLM в приложение для базовых сценариев не требуется.

### Внутренние инструменты

Использовать поставляемые с macOS/Xcode средства по назначению: simctl для устройств, системные API для метрик, top/vm_stat как средства сверки и диагностики. Существующий bash-скрипт — вспомогательный прототип. Не включать произвольный shell, универсальный kill или скачивание сторонних «RAM cleaners» в публичный API.

### CLI

Предлагаемый контракт:

```text
zapas status --json
zapas processes --sort memory --json
zapas tabs list --json
zapas tabs discard --ids 12,34 --apply
zapas simulators list --json
zapas simulators shutdown --udid <UDID> --apply
zapas actions preview --type discard-tabs --ids 12,34
zapas history --json
zapas mcp serve
```

Чтение доступно без флагов изменения. Изменения требуют явного набора объектов и --apply; при подозрительном/изменившемся состоянии ядро отказывает или требует обновлённый preview. Для сложных действий использовать план с коротким сроком жизни и одноразовым идентификатором. В неинтерактивном режиме не зависать на диалоге: вернуть понятное состояние «требуется действие пользователя». JSON содержит версии схемы, время измерения, источник метрик и структурированные ошибки.

Если GUI уже работает, CLI обращается к его локальному сервису через IPC, вместо запуска второго постоянного монитора. Без GUI чтение может работать разовым замером; действия с Chrome требуют подключённой интеграции. Способ IPC и lifecycle проверить на этапе A.

### Собственный MCP-сервер

Для первой версии локальный транспорт stdio, сервер запускается командой zapas mcp serve. Сервер предоставляет диагностические tools: get_memory_status, list_heavy_processes, list_tabs, list_simulators, preview_action, get_action_result. Типизированный execute_action принимает ранее сформированный план, а не shell-команду.

По умолчанию подключение MCP разрешает только чтение. Управление включается пользователем отдельно с выбором допустимых действий. Запрос изменения показывает конкретные объекты в GUI; подтверждённый план связан с точными идентификаторами, версией состояния и сроком действия. Повторно проверить объекты перед исполнением. Не доверять тексту названия вкладки или ответа внешнего сервера как команде.

Вызовы MCP показывать в истории приложения. Задать корректные readOnlyHint/destructiveHint/idempotentHint, но не считать annotations механизмом авторизации. Возвращать actual result отдельно от предполагаемого эффекта. Для клиентов без возможности локального подтверждения оставить режим чтения. Подключение к Codex/другому клиенту пользователь выполняет отдельным установочным шагом; наличие сервера не означает автоматическое подключение.

В GUI чужие MCP-серверы не нужны для MVP. Их добавление потребовало бы MCP-клиента, разрешений и проверки доверия; оно не улучшит измерение RAM само по себе. Нативные системные API и расширение Chrome предпочтительнее зависимости от универсального сервера управления компьютером.

Порядок реализации: контракт ядра и JSON сформировать на этапе B; CLI чтения — вместе с диагностикой; CLI действий — вместе с соответствующими интеграциями; MCP чтения — после стабильного CLI; MCP управления — после подтверждения действий и журналирования. Не задерживать полезный GUI ради полной MCP-платформы.

- [Chrome: processes API](https://developer.chrome.com/docs/extensions/reference/api/processes) — ограничение Dev channel и процессные метрики.

- [Charles: Web Interface](https://www.charlesproxy.com/documentation/using-charles/web-interface/) — исследуемая интеграция управления.
